# 牌库交换与软扩容机制 V2（设计基线）

> **裁决日期**：2026-11-06  
> **状态**：**机制设计已确认；Unity 实现尚未迁移；具体卡牌内容与数值待重新设计。**  
> **规则正本**：本文覆盖旧版 [05·Meta系统](./05-Meta系统.md) §2 中“牌库自然增长/主动删除”的规则，并约束战斗奖励、商店、事件、复制与存档的未来迁移。现行游戏构建仍执行 V1，不得把本文标作“已实装”。  
> **保持不变**：[01·核心战斗机制](./01-核心战斗机制.md) 的 4×4 桌面、每库内卡战斗生成 2 份、同名/词条匹配、行动条与补牌结算规则，除未来另案明确修改外均不随本提案变化。

## 1. 设计目的与判断标准

《记忆勇者》的玩法应形成三个相互反馈的决策层：战斗中的记忆/翻牌与行动条管理，战斗后的有限位置交换构筑，以及整局中以金币和遭遇机会投资容量。让“牌多”既可以承载更多联动，也真实承担配对密度下降与记忆负担增加的成本；不靠卡牌无限自然增长迫使玩家承担后者。

**尚未证明的命题**：这套机制是否真正比 V1 有趣、是否有足够多有意义的决策，必须通过对照跑数和真实玩家试玩验证，不以数学配对概率代替体验结论。

## 2. 现行 V2 决策（规则定稿范围）

| 项目 | V2 裁决 |
|---|---|
| 初始库内张数 | **12 张**（具体 12 张卡牌配方待整体卡牌重设计；**不**沿用当前 10 张配置冒充 V2 实装） |
| 初始容量 | **12**，初始牌库填满 |
| 最大容量 | **无设计硬上限**：不设 14/16/任意数字作为最大张数 |
| 扩容来源 | **商店、特殊事件**；原则上单次扩容容量 +1，具体出现频率、价格、事件选项尚待平衡 |
| 扩容后 | 仅容量 +1，**不自动送卡**；库内张数可小于容量 |
| 常规获取 | 战斗后奖励、商店购卡、可选事件得卡均消费 1 个库内位置：不足容量可**添加 / 交换 / 放弃**；已满只能**交换 / 放弃** |
| 交换 | 玩家明确选择 1 张旧库内牌移除、1 张新卡进入；**库内张数不变、容量不变**，旧牌升级和附加态不继承给新牌 |
| 跳过 | 正常三选一奖励可直接跳过，不强迫进行劣质交换；购买/事件中的可选获得在确认前可取消 |
| 同名重复 | 允许；是否交换旧同名卡由玩家决定 |
| 普通删除服务 | **取消**；商店不再提供旧版付费删牌服务，普通精简靠交换完成 |
| 升级、学者被动 | 机制层暂保留既有逐张升级与“获得新卡时 25% 共鸣附加”的原则；随未来卡牌/角色重设计可单独修订 |
| 复制卡牌 | 属于获取行为，不能绕开容量；空位可增加，满容量须交换或取消；旧版复制的升级/附加态细节暂不重设计 |
| 被动/强制获得的诅咒 | **未定**：需要单独确定强制加入、替换限制、净化代价；不得借普通可选交换默认使诅咒无成本消失 |
| 保存 | 库内张数、逐张状态与**当前容量**都应持久化；版本升级兼容策略后续在技术方案确定 |

### 2.1 常规获取流程

```text
战斗奖励三选一 / 商店购买 / 可选事件奖励
    → 预览新卡
    → 牌库张数 < 容量 ?
       ├─ 是：①直接加入（+1 张）；②指定旧卡交换（张数不变）；③放弃
       └─ 否：①指定旧卡交换（张数不变）；②放弃
    → 成功确认后结算购买费用 / 奖励与学者附加判定
```

操作须具有**原子性**：未完成交换选择或用户取消时，不扣金币、不丢旧牌、不增加新牌；不能因中断流程形成容量超额或丢失已购卡。奖励候选的随机种子与重读档确定性保持旧版原则。UI 应同时显示“当前张数 / 当前容量”，并明确“添加”“替换”“跳过”的后果。

### 2.2 扩容流程与软上限

```text
商店服务（消费金币） 或 特殊事件（按选项支付机会成本）
    → 获取扩容机会
    → 容量 +1，牌库张数原样
    → 后续获取时可以选择填满空位，亦可交换或跳过
```

- **没有“最多扩容 N 次”规则**。玩家能达到的容量取决于商店/事件实际出现、资源投入和整局长度。
- 对商店建议使用随本局累计扩容次数**递增的价格**以形成经济软约束；确切价格、增长函数、是否单店只能购买一次均**未定**。
- 对事件建议设置与其他收益互斥的**机会成本**；事件是否可重复、权重及代价尚待设计，避免无成本扩容变成必选。
- 无硬上限是**游戏设计原则**，不排斥实现中的整数溢出防御、存档合法性检查和 UI 安全约束；技术安全边界不能变相作为玩家可感知的固定扩容上限。
- 只对实际库内牌生成战斗副本；空容量不生成卡牌，也不自动填桌。
- **不得**预先引入“奖励候选同名保底、额外共鸣概率、免费重铺、自动万能匹配”等补丁，先验证新构筑机制。

## 3. 对既有系统的迁移边界

1. **战斗核心保持原规则**：牌库每张生成 2 个战斗实例，洗牌后铺最多 16 格；最大匹配判定、正面牌上限与敌人行动条不在本次重做范围。大牌库导致配对密度变化是预期的战略成本，但如变成纯重复劳动，另立证据驱动调整。
2. **RunSession**：需要从无容量约束的 AddCardToLibrary / DuplicateCardAt / RemoveCardAt，迁移到有容量校验、交换提交、扩容提交的业务接口；删除旧普通商店服务后，特殊事件/诅咒净化可能仍需专用内部移除原语，不等于保留面向玩家的普通删除服务。
3. **奖励 UI 与商店**：三选一候选可跳过；取得卡片后支持指定旧卡替换；商店移除位改为扩容服务（正式售价待定）；购卡未完成交换不扣费。
4. **事件与诅咒**：普通自愿获卡遵循空位/交换原则；强制入库、负面卡、净化、事件复制的细则待后续规则设计，避免假设。
5. **角色与卡牌**：当前学者 10 张起始配方、既有 61 张混合奖励池与推荐流派是**V1 已实现历史事实**；V2 只确定起始**数量 12**，不指定新增的两张卡，也不宣称保留旧四流派或现有卡牌数值。卡牌机制与全部卡牌内容后续重新设计。
6. **设计/实现对账**：设计仓 `current-implementation-contract.json` 是**当前实现快照**，不应因本设计裁决而修改；必须在实际改动源码/配置、测试通过并人工对账后再更新对应契约。当前代码与本文不一致是**已知待实现差异**，不是隐性完成。

## 4. 为什么有望更有趣（仍需验证）

| 选择 | 玩家得到的好处 | 玩家付出的代价 |
|---|---|---|
| 交换已有牌 | 更精准地强化构筑，维持桌面熟悉度与重复度 | 失去一个原有功能/已升级位置 |
| 利用空位添加 | 容纳额外功能，不牺牲旧卡 | 降低特定卡牌被抽中的集中度，可能提高记忆成本 |
| 商店扩容 | 用金币购买后续构筑机会 | 少买卡牌/遗物，扩容本身不立即提供战力 |
| 事件扩容 | 可换取长期空间 | 放弃其他事件奖励/承担相应代价 |
| 跳过奖励 | 保护成熟构筑 | 牺牲潜在进步 |

**失败迹象**：扩容总是无条件正确；所有玩家只交换同一种最优卡组；大牌库的主要差异仅是无效翻牌与重铺次数增长；交换流程频繁打断 Run 节奏；玩家连续跳过奖励而失去成长感。

## 5. 机制验证计划（先于卡牌重做与正式实现）

- **A/B 基线**：V1 自然加牌 vs V2 12 张起步/交换构筑/可扩容，尽量共用战斗规则、敌人与测试种子。
- **策略组**：始终交换并维持 12 张；适度扩容后按需添加；见扩容就扩并优先添加；模拟随机交换策略作为对照。
- **自动化指标**：每次成功配对所需翻牌数、初始/各批次最大匹配数、重铺次数、敌人行动次数、单场时长代理、战斗胜率、获得奖励后跳过/交换/添加比例、扩容购买次数及金币机会成本。
- **真实试玩**：至少包含新玩家与熟练记忆玩家；记录“扩容让我更强还是更累”、何时愿意替换卡、是否能预测和管理额外复杂度，重点比较前中后期。
- **技术边界测试**：满/未满交换、取消不扣费、扩容不送卡、复制不绕容量、存读档、随机复现、容量大于 16 时的桌面和补牌逻辑。
- **卡牌重做**：本阶段明确延后；不要以当前卡池模拟结论证明 V2 最终卡牌平衡，也不要在此文档中定新初始牌内容。
